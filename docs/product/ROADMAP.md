# 实施清单与验收

依据：[产品方案 v0.2.0](versions/v0.2.0.md)。本文件是待办，不表示功能已实现。日期与工期需在开始实施后评估。

## 一、先明确现状

现有 Web v0.1.0 已有独立账号、饮食记录、公开／私密、动态投票、点赞、基础成就、饭点设置和日历导出。新产品规则尚未落地。最近线上检查证实页面和未登录会话接口可用，不能据此宣称完整两账号审批流程已在线上验收。

## 三、验收矩阵

| 场景 | 预期 |
|---|---|
| 早餐私密记录；他人猜中编号 | 本人可读写；他人请求无内容返回；不生成审批单 |
| 先安排午餐、再实际吃不同内容 | 计划与实际同时保留；仅实际进入饮食统计 |
| 额外饮品“想喝”与“已喝补记” | 前者可审批；后者直接记录，不能伪装事前审批 |
| 未授权今日摘要但发布本单 | 广场 API 中没有私密三餐、体重、周期备注、邮箱 |
| 修改公开食物／份量 | 已提交单不可修改；撤回并重新提交不带入旧票 |
| 自投、匿名投票、重复点票 | 分别拒绝、要求登录、幂等；每人每单唯一票 |
| 截止前改票／撤票 | 有效计数正确；撤票不计参与成就 |
| 截止时 2:1、1:2、2:2、2:0 | 分别允许、暂不允许、暂不允许、意见不足 |
| 截止时间与投票同时到达 | 服务端时钟和数据库锁决定；结算后不能写入新票 |
| 服务休眠跨过截止时间 | 下一次读取正确结算；页面倒计时不决定结果 |
| 暂不允许后仍吃、允许后没吃 | 均可回填，不处罚，不改原审批结果 |
| 回填重复请求／超时重试 | 一张审批不生成多条实际记录；成功后可恢复状态 |
| 撤回／隐藏公开内容 | 广场和详情不再返回，新的投票被拒绝 |
| 3 餐记录 + 2 餐计划 + 回顾 | 记录分 93；额外甜点不扣分；缺数据不是健康不合格 |
| 3 允许 + 2 暂不允许 + 3 不足 + 2 待投 | 通过率 60%，有效分母 5，不足和待投分别展示 |
| 时区变化、午夜、历史补记 | 既有记录当地日不漂移，UTC 截止准确，计划分不事后伪增 |
| 旧版数据升级与重新执行迁移 | 无丢失、无重复；legacy 审批不混入新通过率 |
| 页面卡住、会话过期、断网保存 | 有可理解的状态与重试；不丢本次编辑内容、不假报成功 |
| 隐藏分数／关闭 AI 语气 | 普通记录和审批继续使用；不默认分享身体数据 |
| 两个真实独立测试账号 | A 创建公开申请，B 投票；用额外测试账号达到门槛；验证私密隔离、结算、回填、退出重登 |

三票门槛的上线端到端验证需要 1 个申请者 + 3 个投票者，或在隔离环境注入已标明的票数夹具；不能用生产多账号刷真实用户的票。最低两账号测试只验证基本跨用户权限，不足以覆盖三票结算。

## 四、v0.3 候选

可选身体观察、带来源的营养数据、真实 AI 回顾、好友范围、照片。各自先做一小组原型和数据授权评审，再分版本实施，避免一次把敏感数据和模型成本全部引入。

## 五、微信小程序

先复用相同服务端规则和私密权限，再做微信登录与现有账号的显式绑定，不能只凭同名合并账号。服务域名、主体资质、隐私声明、审核、订阅消息等要求在实施时核验微信官方最新规则；Render 地址可以浏览器访问不代表自动符合小程序上线条件。

上线顺序：Web 闭环验证 → 核实主体与平台接入条件 → 小程序开发与测试 → 审核通过后发布。当前未创建、未提交或上线小程序。
