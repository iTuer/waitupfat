# 嘴巴等等我：拍照优先 MVP v0.3.0

日期：2026-10-27（Asia/Shanghai）。状态：产品设计基线，尚未实施。当前应用仍为 v0.1.0。

本版承接 [v0.2.0](v0.2.0.md) 的记录、陪伴和用户自主原则，调整首版优先级。来源是用户明确反馈：手动登记太多；应该先拍照，即使识别不准，也让用户调整，而不是全部填写。冲突处以本版为准；旧版快照保留。

## 一、最小价值

用户把这一餐拍下来，系统先替用户整理，用户只纠正错误，确认后以后能找回。

第一目标不是识别所有营养素，也不是让用户完成一套饮食管理流程；是显著减少记一餐的输入负担。用户允许不完美识别，不代表可以静默保存错误、伪造识别结果或把未知当作零。

首页主入口：**拍照记一餐**。相册导入作为同等可用的入口；一句话记录和常吃复用作为辅助入口。旧的多字段表单退到“编辑详情”，不要求每天先填写三餐计划。

## 二、主流程

**拍照／选图 → 自动整理餐食卡片 → 必要时修改 → 点“记下这餐” → 历史可见。**

用户拍一张午餐照片，识别卡可以显示：

> 这餐看起来有：米饭、鸡蛋、青菜。
> [米饭 ×] [鸡蛋 ×] [青菜 ×] [+ 补一个]
> 今天 · 午餐　[修改]
> [记下这餐]

示例只说明交互，不表示已有识别能力。无误时无需打字；识别错一个食物，直接点它改名；漏识别时加一个标签，也可一句话说“不是鸡肉，是豆腐”。修正整个列表不应比重新填表更复杂。

确认后给出明确保存状态和记录卡片；失败保留当前编辑，允许重试。相同请求重试不能创建重复记录。用户可以随时返回修改已保存记录。

## 三、哪些事情由系统承担

| 内容 | 默认行为 | 用户是否必须填写 |
|---|---|---|
| 食物名称 | 图像识别生成可编辑标签；不确定项标“待确认” | 不强制；失败时可先存照片 |
| 时间 | 默认当前时间，拍旧照片时可调整 | 不必填写 |
| 餐次 | 根据当前时间提供可改的建议，允许“不分类” | 不必填写 |
| 份量 | 不要求克重；可选少量／常规／较多或文字 | 不必填写 |
| 公开范围 | 默认私密 | 不必选择；公开需另行主动操作 |
| 热量、糖、油、钠 | 首版不生成精确数值，不是保存前置条件 | 不必填写 |
| 心情、原因、备注 | 收进详情 | 不必填写 |

餐次与时间的自动填入是便利默认值，不是根据照片推断出的事实。相册照片可能是旧餐、菜单、共享餐桌或只吃了一部分；确认文案应允许用户改时间、删去不属于自己的食物。照片本身不能证明用户实际吃完了。

多道菜只形成一条餐记录，食品标签是该记录的组成；再次拍照可以作为同餐补图，不能默认每张图片都是独立一餐。首版主流程一张图即可，复杂多图编辑延后。

## 四、承认不确定，但不把工作退回给用户

- 识别不确定：指出具体不确定的食物标签，允许一键删除或改名，不让用户核对十几个营养数字。
- 图片模糊／非食物：提示重新拍，也提供“先保存照片”；不强迫填表。
- 识别慢／服务失败：提供“先记下，之后再补”和重试。上传成功且服务端记录提交后，才显示“已保存”。
- 没有网络：显示“尚未上传／保存”，保留当前页面草稿并提醒不要关闭；离线跨重启持久保存不是本版已承诺能力。
- 用户已经手动修正：迟到的识别结果不能自动覆盖；提供“查看识别建议”，由用户选择是否采用。
- 不确定份量：留空。未识别不是没吃，照片记录也算一条有效记录，不扣分。

识别状态与保存状态独立：待识别／识别中／已生成建议／失败，草稿／已确认保存。只存照片的记录展示“待补充”，与已确认标签区分；普通饮食统计可以计记录次数，但不能把它当作完整营养数据。

## 五、互动是可选的第二步

记录卡片保存后可点“问问饭友”，并预览要公开的照片、标签和说明。记录成功不以发布、审批或等待投票为前提。

已经吃过的餐食只能分享或征求回顾建议，不回溯申请允许；额外想吃的东西可从“想吃这个，问问饭友”入口创建独立申请。未吃的照片卡不能先算成实际饮食，最终选择后再关联一条实际记录。

三餐记录与额外审批分离的方向继续保留；v0.2.0 的三票、30 分钟和正式结算规则不再是拍照 MVP 的发布依赖，等待试用决定。现有 v0.1.0 投票属于旧版规则，不能因为文档更新声称已经移除。

## 六、第一版页面与范围

主页面只突出：拍照记一餐、今天的餐食卡、查看历史。点卡片能看照片、食物标签、日期和修改入口。保留既有登录，避免新增注册问卷。

**本版必须有：** 拍照／相册导入、真实图像识别、快捷纠错、私密保存、照片可回看、失败处理与重试、原有记录兼容。

**可作为降级：** 只保存照片、简短文字补记；这些是故障兜底，不能用来冒充拍照识别已完成。

**延后：** 三餐计划、今日评分、复杂成就、营养精算、体重与体脂、AI 陪伴语气调试、随机小组、PK、新平台。既有功能可以暂时保留，但不占主流程、不阻塞记录。

下一版首先验证“拍照记录是否比填表轻松”，不是同时重做全部社交能力。

## 七、实现约束与数据规则

应用仍以 Web 验证。需要的新增能力是图片上传、持久对象存储、图像识别服务、可编辑标签及对应权限。供应商尚未选择，费用预算尚未授权，不能声称免费额度能覆盖真实图片或模型调用。

1. 上传校验文件类型和大小，纠正图片方向、压缩后再发送；相机权限不通过时仍能选图。具体压缩阈值和 HEIC 等格式兼容需通过目标手机验证。
2. 图片不能保存在 Render 临时磁盘上作为长期记录；私密图片需受鉴权保护，不能依靠难猜的公开链接保护隐私。日志与 GitHub 不保存原图、签名地址或个人记录。
3. 发送图片给模型前在产品中说明用途和实际处理方，取得用户对处理流程的知情选择；去除不需要的位置等元数据。公开分享另行确认，不能因为使用识别就自动公开照片。
4. 上传草稿、已保存照片、删除记录的清理策略需在存储供应商确定后落实并验证；保留期限必须与实际配置一致，不能只写文案。导出和删除权限纳入图片能力的实现设计。
5. 保存照片与记录的关联应保证可恢复：以请求编号防重复；识别失败不阻止确认保存；用户确认后的字段不能被后台回写覆盖。
6. 建议新增 photo_assets、识别任务与餐食条目数据，关联原 meals；旧文字记录不强制补图，已有账号与历史继续可读。增量迁移，不改历史迁移文件。
7. 模型结果校验结构和长度；照片中的文字视为数据，不作为系统指令。不替用户执行公开、删除等动作。模型不可用时显示真实状态，不使用随机标签或固定结果模拟识别。
8. 自动识别是此次核心价值，必须做实际接入和实图测试后才算完成。原型、照片上传和真实识别分别标明状态。

## 八、验收与验证

- 一张清晰餐照：正确识别时，从获得识别建议到保存不需要键盘输入，只需一次确认。
- 一个识别错误：可以单独改一个标签，不用重填整餐；漏识别可加标签。
- 上传失败、识别失败、无网络：分别提示；不假报成功、不清空当前照片和编辑。
- 用户修改后识别请求才返回：用户修改保留，自动结果不覆盖。
- 重复点保存、断网重试：只有一条记录。
- 今日拍照、隔天重登：原图和修正后的标签仍可找到；用旧照片可调整用餐时间。
- 他人账号、未登录、过期图片链接：不得读取私密图片或记录。
- 图片默认不公开，公开预览一致；分享已吃内容不会产生事前审批。
- 旧文字记录、旧投票不丢失，不因上线照片能力重新计票。
- 真实模型测试：使用有授权且不含无关个人信息的样图，覆盖混合菜、汤、遮挡、外卖包装和模糊图片；分别记录需要纠正什么，不只报告一个笼统准确率。

可用性目标建议：除首次权限说明外，用户主动操作时间中位数约 10 秒；正常网络下端到端中位数约 20 秒。两者是待验证目标，不是承诺；另外报告模型等待和慢请求，不隐藏免费服务冷启动。主要看无键盘保存占比、纠错耗时、保存失败、次日回看和重复使用，而不以高估算精度掩盖高操作成本。

## 九、版本与下一步

本次只更改产品设计和实施优先级。应用下一版的编号在实际开发发布时确定，不能把方案 v0.3.0 当作应用升级。实施顺序见 [路线](../ROADMAP.md)，本次决策见 [ADR-002](../../decisions/002-photo-first-mvp.md)。

先验证照片识别与纠错原型，再接入可靠保存与历史；供应商、成本和数据处理条件具备后，才能启动真实线上图片识别。无需用户预先补齐食物库，也不要求每个人手动记录全部细节。
