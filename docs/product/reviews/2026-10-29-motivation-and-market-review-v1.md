# 新动机与市场观察评估 v1

日期：2026-10-29（Asia/Shanghai）。依据：用户更新的“为什么想做这件事”“市场上其他的产品做对了什么，我们还有哪些可以做的”及其中两份研究整理。

性质：对新想法的独立评估，不覆盖私人原稿，不替代 [方案 v0.4.0](https://github.com/iTuer/waitupfat/blob/plan/v0.4.0/docs/product/versions/v0.4.0.md)，不升级应用。以下流程与实验均为建议，未实施。公共仓库不保存原稿、个人数据、内部菜单或截图。

## 一、这次真正推进了什么

核心已经更接近：**在用户真实的预算、时间、口味和可购买范围内，帮助他选出愿意吃、能够落实的一餐。**

相对 v0.4.0，本次最重要的增量并不是更多营养分析，而是用户提出的“地点＋菜单”：过去主要知道用户已经吃了什么，现在还需要知道他接下来实际能买到什么。

| 更新 | 判断 | 对产品的影响 |
|---|---|---|
| 将工作、预算、环境和口味纳入问题 | 值得保留，但宏观材料不能替代具体用户访谈 | 建议先问选择约束，避免推荐用户根本无法执行的做法 |
| 从食谱转向实际选择 | 是更明确的切入点 | 第一轮聚焦固定食堂或常点外卖，不同时解决居家烹饪、采购与全国探店 |
| 地点＋菜单可复用 | 本轮最值得验证的产品假设 | 建立“可选餐单”；区分供应菜单、已吃记录和烹饪食谱 |
| 同一场所的人共用菜单 | 比纯投票多了一种社区价值 | 一个人整理、多人受益，不要求每餐都即时获得回应 |
| 减少羞耻与强制限制 | 与拍照低负担方向一致 | 用户可以不接受建议，记录后也可以不看点评 |
| 戒断、补救等表达 | 与上述理念存在张力 | 改为增加可接受的替代、下一次的小调整，不把一餐当作需要偿还的错误 |

这可以形成更具体的定位提案：**帮经常在食堂和外卖中做选择的人，在现有条件里吃得更合适、少一点纠结。** 仍需验证其需求强度，不称为已发现市场空白。

## 二、第一份文档：保留现实约束，缩短论证链

### 2.1 推荐的论证顺序

1. 一部分人想改善饮食，但每天能投入的时间、钱和选择范围有限。
2. 通用知识还需要被翻译成“我眼前这份菜单该怎么选”；这是待访谈验证的困难。
3. 产品把菜单、个人偏好和近期记录放在一起，提供少量具体选择及理由。
4. 用户自行决定，吃过后轻量记录；系统逐步记住什么买得到、什么愿意再吃。

人口健康统计只用一段交代背景。疾病负担大，不足以证明目标用户想用这个工具，更不足以证明社区或付费 AI 会有效。

### 2.2 事实与表述核对

| 原稿涉及的论点 | 评估及建议 |
|---|---|
| 34.3% 与 16.4% | 已准确写出 2018 年。所链接文件标题实际为《体重管理指导原则（2024 年版）》，应与“肥胖症诊疗指南”区分。2030 年数值为条件性研究预测，不是观测事实。[官方文件](https://www.nhc.gov.cn/wjw/c100378/202412/f3f58b54fbeb4c87b14164fac898bf08/files/1736390749000_59785.pdf) |
| 2025 年周工作 48.6 小时 | 国家统计局年终发布中确实列出该数值，但其指标对象是企业就业人员，不能直接外推为全体劳动者或特定行业。该段混列月度与年度指标，引用时不要自行写成全年平均，更不能由此证明某群体工时持续增长。[原始发布](https://www.stats.gov.cn/sj/zxfb/202601/t20260119_1962330.html) |
| 人均可支配收入 43,377 元说明餐饮预算降低 | 数值是 2025 年官方数据，但收入水平本身不能证明餐饮预算下降；该发布同时报告收入增长。需要另有目标人群预算或支出变化证据。[国家统计局](https://www.stats.gov.cn/sj/zxfb/202601/t20260119_1962321.html) |
| 全国每单餐饮消费 34.7–39.8 元 | 本次未核实能把这两个数放在同一口径下的原始报告。需分别确认年份、堂食／外卖、样本平台、人均／每单，不能将不同值拼成全国统一区间，也不能直接证明可支配能力下降。 |
| 喝汤被证明不健康 | 不宜对整个食物类别做绝对判断。应描述具体配方、盐脂含量、份量和适用人群；WHO 的健康饮食原则也不能推出所有汤都不健康。[WHO](https://www.who.int/news-room/fact-sheets/detail/healthy-diet) |
| 禽类供应多，所以少吃红肉会缺铁锌 | 用户引用的研究整理已区分食材词频、上架菜数和摄入量，应把这个边界带回正文。营养缺乏不能由某类菜出现频率推断；铁来源还包括禽肉、海鲜、豆类和强化食品，整体摄入与吸收需要另评估。[NIH 铁资料](https://ods.od.nih.gov/factsheets/Iron-HealthProfessional/) |
| 果汁／果味酸奶中的果糖造成极大负担 | 改成关注具体产品的游离糖或添加糖、份量与饮用频率，不把果味、果糖和某种疾病结果直接等同。WHO 将果汁中的糖计入游离糖，并建议限制其摄入；这不支持对所有水果或酸奶做同一判断。[WHO](https://www.who.int/news-room/fact-sheets/detail/healthy-diet) |
| 孤独会导致暴食，社区可以解决 | 应保留“可能相关”的表述。引用整理本身已明确不能确定因果；其中 2025 年研究的 49 人样本、11 天观察也未发现不同孤独轨迹的每日暴食症状显著差异。不能由此声称匿名投票能改善暴食。[研究原文摘要](https://pubmed.ncbi.nlm.nih.gov/40399706/) |

菜品看起来健康不代表知道制作油量，这个观察值得保留；但不能反过来假定每家饭店的炒菜都用油过量。产品宜标注“油量未知”，而不是靠图像给出确定的油、糖、钠数值。

### 2.3 让语言与产品行为保持一致

| 容易引起误解的表达 | 建议表达与实际行为 |
|---|---|
| 戒断高热量食物 | 增加愿意接受的替代选择，减少不由自主的重复选择；不把所有喜欢高热量食物的人视为成瘾 |
| 吃完提供补救措施 | 下一次可以尝试一个小调整；不安排禁食、跳餐或运动来“抵消”这餐 |
| 每次分享都得到建议 | 默认先完成记录；“想听建议”再展开。避免每次进食都变成被检查 |
| 让大家同意后安心吃 | 可以征求意见，但最终决定属于用户；零票或反对不应变成吃饭许可 |
| 不喜欢控制，所以没有目标 | 提供可选目标与反馈强度，接受自主使用数据的人；不强制所有人使用同一种方式 |

理念上的温和必须落在默认值、流程与失败反馈里。即使用温柔文案，如果首页仍然是红色超标提示、每餐强制点评或通过率排名，实际体验仍可能与理念相反。

## 三、第二份文档：从产品清单转向证据和具体任务

### 3.1 最值得保留的结论

单独做拍照、营养分析、食谱推荐或社区，不足以形成差异。新的可能性在于：**在已确认的可选菜单里，结合用户的条件给建议，并验证是否真的买得到、愿意吃、愿意再用。**

创作者可以提供表达方法、知识组织和服务形式的参考；不能把个人创作者观点直接变成 AI 的科学规则。App 比的是操作、价值与限制，内容社区比的是问题和回应，三者不要放在同一功能勾选表里就直接比较优劣。

### 3.2 本轮抽查结果

| 对象 | 本次核实到什么 | 不能据此断言什么 |
|---|---|---|
| 薄荷健康 | 官网明确介绍拍照识别、营养数据、饮食建议及健康记录分析。[官网](https://www.iboohee.com/) | 宣传不等于已测准确率；原稿关于严格限制、逆反与放弃应保留为体验观察／待测假设，不能外推全部用户 |
| See How You Eat | 官方定位明确包含照片日记、不数卡路里和低压力记录。[官网](https://seehowyoueat.com/) | “所有 App 都要求严格身体数据和热量限制”不成立；低负担本身并非独有能力 |
| Samsung Food | 官方说明食谱保存、社区分享、周菜单和购物衔接。[官网](https://samsungfood.com/) | 不能从其功能说明推断已解决中国食堂现售菜单问题，也不能据此证明我们有市场空间 |
| 记一餐 | 已尝试访问给定 App Store 链接，但本次未成功核实页面内容 | 暂按原稿提供的待核实线索，不把具体功能或权益当作独立确认结果 |
| 其他创作者、App、社区 | 作为后续研究池保留，本次不逐一实机检查 | 不确认其当前价格、功能完整性、专业资格或健康建议有效性 |

这次没有在指定项目中找到原稿引用的进度条截图，不把它当作已查看的界面证据。两份研究整理已阅读，但外卖论文全文下载未成功，本次不背书其中未复核的百分比。

### 3.3 下一轮只做三个同题任务

1. 给一个真实但去标识的食堂菜单、预算和不能接受的食材，观察各工具是否能给出菜单中存在的选项。
2. 对同一张餐照，观察识别错误后怎么改、多久能保存、是否必须补身体资料，以及能否关闭点评。
3. 吃完后第二天再打开，观察能否复用菜单、替换缺货选项、找回实际记录。

建议优先比较薄荷的完整能力、See How You Eat 的低负担记录、Samsung Food 的内容复用；记一餐核实可访问版本后加入。创作者研究先聚焦“如何解释一个小调整”，不用继续扩充名单。对照组应包括用户目前的方法及“通用 AI＋同一张菜单”，否则不能判断专门做 App 的额外价值。

## 四、把“地点＋菜单”变成可测试的产品对象

### 4.1 三种东西不要混在一起

| 对象 | 回答的问题 | 例子（仅示意） |
|---|---|---|
| 可选餐单 | 这个场所／时间能选什么 | 某食堂午餐窗口当天菜单 |
| 用餐选择 | 用户准备选哪个 | 今天选菜单中的 A 套餐，可附简单偏好 |
| 实际记录 | 最后吃了什么 | A 套餐缺货，实际换成 B；餐照确认后保存 |

烹饪食谱另含原料、步骤和制作条件，暂不作为不能自己做饭用户的默认对象。把一切都称“食谱”会混淆供应信息与用户摄入。

### 4.2 建议的小闭环

**拍一张菜单 → 系统整理并让用户确认 → 带入预算或复用常用条件 → 给出 2–3 个实际候选 → 自己选／邀请帮选 → 吃过后确认记录 → 下次复用。**

第一天没有饮食历史也能用：先根据菜单和明确约束提供候选，历史只逐步增强建议。菜单只有名称时，模型不应编造配方、准确油盐、过敏原或精确营养数值；无法确定时保留不确定项。

一次导入后的重复使用必须更简单：默认记住常用场所和菜单，下一次只确认是否更新。预算、忌口和口味按需问、可复用；不能把“四个条件”设计成每次必填四个框。

示意反馈：“根据你刚确认的菜单和预算，可以比较 A 与 B；如果 A 今天没有，就选 B。你更想吃哪一个？”这里的 A、B 必须来自实际菜单，例子不构成营养处方。用户可选第三个或不接受建议。

### 4.3 最小信息与真实成本

- **餐单**：场所别名、日期／时段、来源、最后确认时间、可见范围。首版无需精准定位，避免暴露固定工作或学习地点。
- **菜品**：名称、已知价格、可售状态、来源片段；识别不确定项可局部修改。未知价格不能默认满足预算，截图里的折扣也不能假设一直有效。
- **可用性**：过期、今天没有、价格变化各有反馈；模型不能把旧菜单当实时库存。
- **版本**：一次更新生成新版本；投票与历史指向当时的菜单版本，不因今天改价而改写过去。
- **私密与共用**：默认个人餐单；用户主动分享经过裁剪的菜单信息。内部标识、联系方式和其他人个人信息不随图上传公开。
- **维护**：每个人可从共享模板复制个人版本；修订带来源与时间，不直接覆盖他人的记录。供餐方资料和用户观察要有区分。

这部分的运营成本不能忽略：谁首次整理、多久更新、OCR 纠错要花多久、过期后谁维护，都可能吞掉“省事”的价值。首版只试一个场所，不做全国菜单库、自动抓取或批量九图导入。

### 4.4 社区的先后顺序

建议先验证共用餐单与小范围经验，再验证即时匿名投票。共用菜单、确认今天供应什么、说明分量和等候情况，都能帮助后来的人；即时投票仍受饭点在线人数限制。

社区负责真实供应、口味、价格与体验信息；AI 负责整理、依据明确约束比较并解释不确定性。公众票数不能覆盖用户忌口，也不能证明食物营养适合度。“同一地点”是内容复用边界，不代表必须新建聊天群或公开成员身份。

如果试用者只复用菜单、不想投票，也可能是有效结果；不必为了保留最初的审批创意强行加入互动步骤。

## 五、与现有方案如何衔接

| 现有 v0.4.0 | 本轮建议 | 状态 |
|---|---|---|
| 先让拍照记录可靠 | 继续保留，尤其隔天回看和权限隔离 | 方向不变 |
| 知道用户吃过什么，再辅助选择 | 增加“真实可选菜单”，没历史也能先体验选择价值 | 新研究假设，未排入开发 |
| 社区帮选＋收藏 | 优先测试菜单复用和有限范围的经验，投票可选 | 建议，不改旧规则 |
| AI 回顾与安排作为付费候选 | 优先观察“少花时间且建议买得到”的价值；预算敏感人群未必愿意订阅 | 商业假设待验证，不定价 |
| 温和、可选的反馈 | 明确不强制逐餐点评，不以补救名义制造补偿任务 | 作为评审建议记录 |

本次不直接发布 v0.5.0：菜单导入会增加新的对象、维护与权限成本，先测试是否值得。正式采纳后再新增方案快照、决策与实施任务，避免文档扩张替代用户验证。

## 六、下一步最小实验

建议在一个愿意配合的固定用餐场所，找约 5 位成年人试用 5 个工作日。这是探索性规模，不代表统计检验充分，也不是已发出的招募或日程安排。

1. 第一天观察他们原本怎么选、花多久、放弃哪些选项；不先教他们必须怎么吃。
2. 使用经允许、去标识的一份实际菜单做低保真原型；可由人整理，但必须明确人工辅助，不能伪装自动识别已实现。
3. 给少量候选，分别记录“愿不愿意选”和“能不能买到”，实际选择变化及原因可选回填。
4. 后几天让人自行决定是否再用，观察复用菜单是否真的省事；菜单上传者与使用者的成本分别记录。
5. 与原方法、通用 AI 用同一菜单的体验比较；小样本可交替体验顺序，但不声称证明健康改善或长期留存。

优先看四类证据：

- **可执行**：实际可以买到且满足已知预算与明确限制的候选数／全部推荐候选数；未知信息单列。
- **省事**：从开始选择到决定的主动耗时和等待耗时，单列首次导入与后续复用。
- **回用**：后续有就餐机会的人里，多少人主动再打开；展示分子分母，不以提醒后的被动操作代替。
- **额外价值**：相比原方法与通用 AI，具体省掉什么工作；不接受建议的理由是什么。

如果真实菜单仍不能使建议可执行，先修数据与范围；如果用户只需要照片日记，继续记录主线；如果菜单复用有效而投票无人参与，就暂缓社区投票。不会因“已有很多研究”就默认三条路线都应开发。

## 七、可用于下一版开篇的表述建议

很多人希望吃得更合适，但每天的选择受预算、时间、场所和口味影响。知道一个理想的食谱，并不等于眼前能买到、愿意吃，也不等于能够持续执行。

我们想先服务那些经常在食堂和外卖中做选择的人：从真实菜单出发，结合明确偏好与近期记录，给出少量能落实的选择。用户自己决定，吃过后随手记下；有用的菜单和经验可以复用。

产品不要求每餐完美，也不把喜欢某种食物视为错误。我们希望减少选择和记录的负担，让下一次的小调整更容易发生。它是否有用，需要通过真实使用验证。
