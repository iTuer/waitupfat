# 核心场景评估 v1

日期：2026-10-27（Asia/Shanghai）。对象：用户更新草稿中的 3.1 三餐记录、3.2 广场帮选、3.3 AI 推荐、3.4 收藏偏好。

性质：独立产品评估与建议，不自动采纳所有新增功能，不改变 [方案 v0.3.0](../versions/v0.3.0.md) 或已部署应用。未做本轮原型、模型或付费实验；不归档私人原稿、个人经历或饮食数据。

## 一、整体判断

这次补全了有潜力的循环：拍照记录实际饮食 → 纠结时发起帮选 → 收藏感兴趣的食物 → 为以后的选择提供参考。四个入口分别对应“吃过什么”“现在选什么”“喜欢什么”“以后怎么搭配”。用户任务比单纯罗列页面更清楚。

需要警惕的是，拍照之后又出现人数、逐项热量、刷新、额度、说明、私密开关、内容审核、会员点评。若这些都成为必经步骤，拍照只是长表单前面增加了一步，仍然没有达到低负担记录的目标。

首版要同时控制两种成本：用户操作成本，以及图片存储、模型调用、内容审核和社区回应的运营成本。会员功能数量不能替代付费价值验证。

## 二、3.1 三餐记录：建议保留照片，重做确认页

### 1. 把“填写页面”改成“识别结果确认卡”

推荐流程：拍照／选图 → 展示识别出的食物标签 → 按需改错 → 确认保存。照片正确且识别无误时，用户不输入文字；人数、说明、份量等放在“调整详情”。

保留“跳过照片”的文字或常吃入口。首次相机权限被拒绝、桌上不方便拍摄时，用户仍能记录。

九张图可以是未来的上限，不能成为设计起点。首版建议一张主图，确有需要再补图。同一盘菜不同角度、菜单截图和实际餐食必须区分；图片数量不是食物数量，更不能每张都加一遍热量。

### 2. “几人餐”不能解决实际吃了多少

四个人吃一桌菜，不代表每人吃四分之一；照片中还有剩菜、汤汁、包装与未食用部分。人数可以选填，但不能拿总热量除以人数就宣称个人摄入。

建议先区分“我这一份／多人共享”。默认展示这张照片的食物内容；共享餐若需要个人摄入估算，再提供可跳过的份量调整。无法确定本人份量时标注未知，仍允许记录，暂不纳入个人热量合计。

### 3. 热量范围不能为好看而收窄

用户提出用区间和允许纠错的方向合理；“差值不要过大”应理解成提高估算质量的研究目标，不能实现为硬裁剪区间。识别食物、估计份量和推算营养是不同环节，照片识别出菜名不代表已经知道摄入量。图像饮食评估研究也将这些环节分别讨论。[研究综述](https://arxiv.org/abs/2108.02947)

例如 400–800 kcal 的示意区间中点为 600，但取中点不会消除不确定性。若 UI 需要一个中心值，应同时保留区间、来源和“估算”标识；用户修改值也需标注为用户修正，不把它升级为测量值。

多个食物估算相加时，区间端点相加只能称粗略上下界，不能称统计置信区间。完全未知的项不能记成零。第一版可先验证食物识别与保存，热量估算作为单独实验，和当前 v0.3.0 不默认输出精确营养数字的方向区分。

### 4. 热量进度条缺了“目标从哪里来”

进度条需要分子、分母和覆盖范围：分子是确认后的实际摄入估算，分母是用户自愿设置或经适当方法取得的个人目标，覆盖范围说明哪些餐有估算、哪些未知。没有记录不等于没有摄入。

个人能量估算通常还涉及年龄、身高、体重、活动情况等；NIDDK 的工具会采集这些信息。这意味着把目标热量设成首屏默认指标，会引入新的设置负担，不能随意给所有人同一个上限。[NIDDK 工具说明](https://www.niddk.nih.gov/bwp)

建议首页优先“今日餐食时间线”，已知部分可显示“已记录食物估算”；用户选择开启热量目标后再出现目标对比。只记录照片、无个人份量或缺少估算时，不显示完整一天已达标／超标。帮选候选菜也不能先算入实际摄入。

## 三、免费三次、刷新和会员：先把计费单位说清楚

每日三次看起来匹配三餐，但还存在补图、拍错、识别错误、饮品和重试。若用户必须付费才能修正系统错误，会伤害信任。

建议明确区分：

| 行为 | 建议规则 |
|---|---|
| 保存照片、手动改标签、修改时间 | 基础记录能力，不消耗识别额度 |
| 新的一餐成功完成识别 | 按一餐计一次，而不是按每张图计一次 |
| 识别失败、超时、重复请求 | 不重复计费；需要明确失败／取消与额度恢复规则 |
| 同一餐重新识别 | 先提供手动纠错；用户主动请求前显示是否消耗额度和剩余额度 |
| 未购买会员或额度用尽 | 仍能保存照片并回看历史，不让付费墙中断记录 |
| 会员权益 | 可测试更高额度、较长周期回顾与搭配建议；不是保障基本记录正确性的前提 |

“三次”是待验证的额度参数。先测一次成功记录平均触发多少次模型调用、模型与图片存储成本、纠错频率，再确定定价。多图、重试和审核均可能增加成本，但未选供应商前不能声称当前免费资源足够。

## 四、私密保存与公开审核要分成两条状态

默认私密值得保留，但“取消私密即公开”容易误触。建议明确的可见范围选择“仅自己／发布广场”，公开前有预览；不是一个反向勾选框。

个人记录保存与社区发布分别反馈：

- 私密记录：已保存，可以在个人历史找到。上传的基本文件安全检查正常执行，不以广场审核通过为保存条件。
- 公开内容：先保证本人记录已保存，再显示“待审核”；通过后才对其他用户可见。
- 审核失败：说明公开失败原因，允许修改或保持私密，不能使用户误以为餐食记录丢失。

审核中／已公开／公开受限是发布状态；是否已保存是持久化状态；识别中／待确认是识别状态。三者分开，才能避免出现“模型好了但记录没存”“审核没过所以我的记录消失”等问题。

若图片包含明显安全风险或违法内容，按相应上传和平台政策处理；不能承诺任何图片都能私密保存。这里讨论的是正常餐照不受社区发布审批阻塞。

## 五、3.2 “吃点啥”：从审批变成帮选，是一个产品决策

“是否允许吃”与“在几个选项里帮我选”解决不同问题。新增草稿更偏后者，建议将它明确为待确认的方向，而不是用原审批状态和通过率去解释。

普通帮选可以覆盖三餐，未必只限额外饮食；若采纳这一点，需新增正式方案与决策记录，说明它与“只有额外饮食审批”的区别。

### 建议首版定义

- 一个问题 + 默认两个选项，建议首版最多四个；九张附图与九个可投选项分别计数。上限四是待测建议，不是既定结论。
- 先支持单选，降低投票规则与结果解释复杂度。多选应明确“最多选几项”和取消选择规则，延后测试。
- 投票人可改票、本人不可投，身份校验仍在后台执行；首页不展示用户真实账号。
- “截止时间”使用分钟／小时等时间单位，“最多票数”使用人数或有效票数，分别配置。原文“最长投票时间 100人”单位冲突，需要改正。
- 若同时设时间与票数上限，明确定义先到者结束；零票显示暂无建议，平票并列展示，不自动宣布唯一赢家。
- 用户可以随时自行选择并回填实际结果。票数表示偏好，不代表营养适合度；不必等投票结束才能正常吃饭。
- AI 预估可以是可隐藏的辅助，但候选截图信息不足时，不展示虚假的确定热量。

无需把这些参数全部摆给发布者。先给可用默认值，更多设置折叠，避免把“帮我选晚饭”变成配置投票系统。

### 匿名的边界

建议匿名面向其他用户，平台仍保留必要的账号关联来实现一人一票、本人管理、举报和反滥用；不能宣传为平台也完全不知道身份。

固定化名有利于持续关系，逐帖匿名更适合一次性发问，两者的取舍需要试用。若所有发布和互动都完全无法关联，反而很难形成你希望的长期陪伴。

## 六、3.3 AI 推荐：三天是体验门槛，不能当作充分了解

“记录三天后推荐”可以作为促活实验，但三个日期各记一杯饮料，和完整记录三天，信息量不同。不要在第三天突然表现得已经了解用户的完整饮食结构。

建议分层：未有历史也能给通用选择；有少量历史时说明参考了哪些记录；有较完整覆盖后再尝试更个性化的搭配。缺失的信息明确展示，不把未记录日或餐次当作没吃。

如果提供菜单搭配，至少允许用户管理明确的过敏／忌口，并说明推荐不能保证过敏原安全。偏好与禁忌分开：收藏不能覆盖禁忌，模型也不能仅从照片或三天历史推断医疗状况。

会员付费可以验证“省去选餐时间”和“回顾是否有用”，不要用“记录满三天才给任何价值”作为唯一回访动机。真实模型、成本、授权和输出质量均尚待验证。

## 七、3.4 “爱吃”：值得保留，先把信号分清

“给我吃一口”有记忆点，适合成为收藏文案；操作后应明确反馈“已加入想吃”，让用户知道它不是给对方追加一票。

至少区分四种信号：

| 信号 | 含义 | 是否可直接当作喜好依据 |
|---|---|---|
| 点赞 | 欣赏内容、支持发布者 | 弱信号，不等于爱吃 |
| 收藏／想吃 | 想以后试试 | 兴趣，不等于已经吃过且喜欢 |
| 吃过且喜欢 | 实际体验后的偏好 | 可作为较强偏好信号 |
| 不感兴趣／忌口 | 内容偏好或明确限制 | 两者还需分别保存，忌口优先 |

建议“别吃了”暂不作为面对作者的公开负反馈，它很容易被理解为评判对方是否有资格吃。若意思是调整推荐，用本人可见的“不感兴趣”；若意思是建议替代方案，放在主动征询意见的卡片里。

收藏可以作为推荐输入，但不能是唯一输入。否则可能不断推荐用户刚收藏的同类内容。用户应能移除、修改或关闭偏好影响；不收藏、不公开也不能失去正常记录功能。

## 八、建议的收敛版本

| 优先级 | 场景 | 首版交付 |
|---|---|---|
| P0 | 记录这餐 | 拍照／选图、食物标签、纠错、私密保存、次日回看、识别与保存失败兜底 |
| P1 | 帮我选 | 两个候选的简单投票、清楚的截止、个人决定回填；先测真实回应 |
| P1 | 想吃清单 | 收藏、移除、回看，暂不依赖模型推荐 |
| 后续实验 | 营养与会员 | 份量修正、估算展示、额度与费用验证、付费回顾／搭配 |

主链建议：**拍完确认就能退出；需要互动再发布；喜欢的内容可收藏。** 不要求每次记录都同时参与热量核算、审批、会员点评和社区互动。

本次值得优先验证的任务：从第一次拍照到找到保存结果，记录完成时长、必需输入次数、纠错步骤；再观察第二天是否愿意继续用。帮选与会员分别做小规模验证，不能由“能上传照片”推断它们已经成立。

## 九、需要下一轮明确的五个问题

1. 社交核心采用“帮选”，还是继续“允许／不允许审批”？是否覆盖普通三餐？
2. 热量是首版核心价值还是辅助实验？如果核心，如何取得个人份量、目标与不确定性？
3. 匿名是固定化名还是逐帖匿名？是否要形成持续关系？
4. 免费额度按餐、按图片还是按成功识别计？纠错／失败如何处理？
5. 多人餐记录整桌，还是个人摄入？共享照片无法确定本人份量时如何展示？

这些都是产品行为选择，不需要用户为每个技术细节拍板。此次评估先将冲突和默认建议写明，待方向确认后再形成新方案快照。当前 v0.3.0 与应用版本保持不变。
