# GitHub 版本与变更记录规则

用户要求：每一次版本和改动都通过 GitHub 记录。本规范适用于本项目后续方案、代码、数据库结构和部署配置变更；只有执行并推送后，才可称“已记录到 GitHub”。它不是外部平台的自动监听器。

## 一、两种版本分开

- 应用版本：`package.json` 的版本号，标签 `app/vX.Y.Z`。当前已部署应用是 0.1.0。
- 产品方案版本：`docs/product/versions/vX.Y.Z.md`，标签 `plan/vX.Y.Z`。当前新方案是 0.3.0，不代表应用版本随之升级；当前应用仍为 0.1.0。
- 每个可独立解释的改动有 Git commit；不是每个 commit 都需要发新版本。
- 修正文案和不改变规则的小修订升 patch；新增流程或改变产品规则升 minor；广泛破坏兼容的重设计升 major。即使 0.x，数据或规则不兼容也必须专门说明。
- 原版本快照和已发布标签不覆盖、不移动；更正内容新增版本并指出替代关系。Git 历史是最终溯源。

## 二、每次改动要留下什么

1. 改动原因：哪个用户问题或故障触发。
2. 改动前后：实际行为差异、适用范围；计划和已实现明确分开。
3. 验证证据：运行了什么、结果如何、哪些尚未验证。纯文档只验证内容、链接和版本一致性，不编造应用测试。
4. 风险与回退：数据兼容、公开范围、迁移依赖、可回退方式；没有影响也直接说明。
5. 更新 `CHANGELOG.md`，重要规则补 `docs/decisions/`，方案修订新增版本文件并更新索引。
6. GitHub 提交只包含本次相关文件；提供 commit 或 PR 链接。代码通常使用 `codex/` 分支和 PR；已授权的纯文档归档可直接提交 main。提交前检查远端是否有新改动，禁止覆盖他人提交。

提交标题示例：`docs(product): archive plan v0.2.0`、`feat(approval): add deadline settlement`、`fix(auth): explain invalid site URL`。

## 三、发布必须另外记

`docs/releases/README.md` 是台账，记录应用版本、代码 SHA、部署平台／时间、迁移编号、验证范围、状态和已知限制。代码推送不等于部署，平台 Live 不等于完整业务验收。

发布步骤：相关测试通过 → 数据迁移／回退准备 → 推送代码 → 部署 → 线上验证 → 更新发布记录并创建 `app/` 标签／Release。应用发布说明至少包含用户变化、已知限制、验证和回退。不要把产品方案提交包装成应用发布。

方案归档提交后创建对应的 `plan/vX.Y.Z` 标签；它只标记文档基线，不触发 Render 手动部署。现有应用的历史部署日期仅按已有证据记录，无法确认的时间留作未知，不编造。

Render 环境变量等在 GitHub 外手动修改后，记录“变量名、变更原因、部署结果”，不提交变量值。无法访问后台时如实标注由用户报告，不能声称已自动跟踪。用户日常饮食数据、密码、连接串、会话、邮箱清单和生产导出永不进入公共仓库。

## 四、后续操作检查表

- [ ] 阅读当前方案、CHANGELOG 与发布状态。
- [ ] 明确本次是设计、实现还是部署；检查远端头和已有本地改动。
- [ ] 完成本次工作及必要验证，更新变更说明与相关规则。
- [ ] 检查仅提交授权范围和无私密数据，推送并验证 GitHub 实际内容。
- [ ] 必要时创建新版本标签；实际部署后再更新台账。
- [ ] 向用户交付内容链接、提交标识、验证结果、未上线部分。

若 GitHub 不可用，保留本地文件并明确“尚未同步”，恢复后补交；不能仅口头答应已经记录。仓库内 [AGENTS.md](../AGENTS.md) 提醒后续协作者执行本规则，但不能保证绕过仓库进行的手动操作被自动捕获。
